# API 通知系统 - 中间件选型说明

## 选型总览

| 组件 | 选择 | 替代方案 |
|------|------|---------|
| 编程语言 | Go | Python / Java / Node.js |
| Web 框架 | gin | 标准库 net/http / echo / fiber |
| 数据库 | PostgreSQL | SQLite / MySQL / Redis |
| DB 驱动 | pgx | lib/pq / database/sql |
| HTTP Client | 标准库 net/http | resty / req |

---

## 逐项说明

### 1. 编程语言：Go

**为什么选 Go：**
- 并发模型天然适合 Worker 轮询模式（goroutine 轻量）
- 编译为单二进制，部署简单，无运行时依赖
- 标准库强大，HTTP/JSON 支持开箱即用
- 适合高并发网络服务

**替代方案：**
- Python：开发快，但并发性能弱，GIL 限制多 Worker
- Java：生态成熟，但启动慢、内存占用高，MVP 过重
- Node.js：异步 IO 好，但单线程，CPU 密集场景弱

### 2. Web 框架：gin

**为什么选 gin：**
- 轻量，路由性能好
- 中间件生态丰富（日志、Recovery、JSON 序列化）
- Go 社区最流行的 Web 框架，上手简单

**替代方案：**
- 标准库 net/http：零依赖，但路由/中间件需手写，MVP 开发效率低
- echo：与 gin 类似，无明显差异，选 gin 因社区更大
- fiber：基于 fasthttp，性能更高但与标准库不兼容，MVP 不需要

### 3. 数据库：PostgreSQL

**为什么选 PostgreSQL：**
- `SELECT ... FOR UPDATE SKIP LOCKED`：原生支持任务抢占，多 Worker 并发安全
- JSONB：`headers` 和 `payload` 直接存 JSON，读写方便，支持索引
- ACID：任务落盘可靠，进程崩溃不丢数据
- `FILTER` 子句：统计聚合查询简洁高效

**替代方案：**
- SQLite：零部署成本，但无 `SKIP LOCKED`，并发弱，只能单 Worker
- MySQL 8.0+：也有 `SKIP LOCKED`，但 JSON 操作不如 PG 的 JSONB 方便
- Redis：可做任务队列，但失去 ACID，查询和管理不方便，宕机有丢数据风险

### 4. DB 驱动：pgx

**为什么选 pgx：**
- Go 生态最成熟的 PostgreSQL 驱动
- 原生协议，性能优于基于 database/sql 的驱动
- 支持 PostgreSQL 特有功能（如 `SKIP LOCKED`、JSONB）
- 连接池内置，无需额外配置

**替代方案：**
- lib/pq：基于 database/sql，兼容性好但已停止维护
- database/sql + 任意驱动：标准接口，但无法利用 PG 特有功能

### 5. HTTP Client：标准库 net/http

**为什么选标准库：**
- 调用外部 API 只需发 HTTP 请求，不需要复杂功能
- 零依赖，无版本风险
- 可自定义超时、Transport，满足 MVP 需求

**替代方案：**
- resty：API 更友好，但增加依赖，MVP 不需要
- req：类似 resty，同理

---

## 为什么没用消息队列

题目允许使用消息队列，但 MVP 阶段选择不用。

**理由：**
- DB 轮询 + `SKIP LOCKED` 已满足并发需求
- 少一个中间件，少一份部署和运维成本
- MVP 流量不大，DB 轮询延迟可接受

**演进时再引入 Kafka/RabbitMQ，触发信号：**
- DB 轮询延迟明显
- 任务量超过单库承载能力
