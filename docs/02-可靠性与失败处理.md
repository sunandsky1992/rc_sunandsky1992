# API 通知系统 - 可靠性与失败处理

## 1. 投递语义

**选择：至少一次（at-least-once）**

| 属性 | 说明 |
|------|------|
| 不丢消息 | 任务落库后才返回"已接收"，进程崩溃也不会丢 |
| 可能重复 | 失败重试可能导致同一通知投递多次 |
| 去重责任 | 由外部供应商处理，我们提供 `notification_id` 供其去重 |

**为什么不用 exactly-once：** 分布式 exactly-once 代价极高，而通知场景下偶尔重复的代价远小于漏投递，是合理的工程取舍。

---

## 2. 失败策略

### 临时性失败（网络抖动、5xx、超时）

- **重试机制**：指数退避
- **退避间隔**：1s → 2s → 4s → 8s → 16s → 32s → 64s → 128s
- **最大重试次数**：8 次
- **重试条件**：HTTP 状态码 >= 500 或网络超时/连接失败

### 长期不可用（重试到底都失败）

- 达到最大重试次数后，任务标记为 `dead` 状态
- 提供管理 API 查看死信任务列表
- MVP 阶段不做自动恢复，支持人工触发重投

---

## 3. 状态流转

```
pending → in_flight → delivered（成功）
                   ↘
                     retrying → in_flight（重试）
                              ↘
                                dead（超过最大重试次数）
```

| 状态 | 含义 |
|------|------|
| `pending` | 已落库，等待投递 |
| `in_flight` | 正在投递中 |
| `retrying` | 投递失败，等待下次重试 |
| `delivered` | 投递成功 |
| `dead` | 超过最大重试次数，进入死信 |
