# API 通知系统 - 系统边界设计

## 背景

企业内部多个业务系统在关键事件发生时，需要调用外部系统供应商提供的 HTTP(S) API 进行通知。本服务作为中间投递层，接收业务系统提交的通知请求，并尽可能可靠地投递到目标地址。

---

## 系统边界

### 要解决的（核心链路）

| 编号 | 能力 | 说明 |
|------|------|------|
| 1 | 接收通知请求 | 业务系统通过 HTTP API 提交通知，指定供应商 + payload |
| 2 | 持久化 | 收到后立即落库，返回"已接收"，不管后续投递成败 |
| 3 | 供应商适配 | 根据 vendor 配置，将请求转为对应供应商的 URL/Header/Body 格式 |
| 4 | 投递 | 异步调用外部 API |
| 5 | 重试 | 失败自动重试，到上限进死信 |

### 不解决的（MVP 不做，后续演进）

| 不做的事 | 理由 | 演进时机 |
|----------|------|----------|
| 通知内容的业务校验 | 业务系统自己保证内容正确，我们只做投递通道 | — |
| 外部 API 返回值的业务处理 | 题目明确说业务系统不关心返回值，我们只需知道送达与否 | — |
| 通知模板管理 | 供应商配置存 DB 即可，不需要模板引擎 | 流量增长、供应商数量多时 |
| 权限认证/租户隔离 | 企业内部服务，MVP 不需要 | 多团队接入时 |
| 限流/熔断 | MVP 先不做 | 外部系统稳定性问题暴露后 |

---

## 设计原则

- **只做投递通道**：不关心通知内容的业务语义，不做内容校验
- **可靠优先**：消息落库后才返回成功，确保不丢
- **MVP 最简**：核心链路全做，其余进演进路线，不过度设计
