# AI 使用说明

## 概述

本作业在 AI 辅助下完成需求分析、方案设计和文档编写。以下是 AI 在各环节的参与情况、未被采纳的建议，以及由本人独立做出的关键决策。

---

## 一、AI 在哪些关键地方提供了帮助

| 环节 | AI 的帮助 | 本人的作用 |
|------|---------|-----------|
| 需求理解 | 解析 PDF 题目，提取并归纳核心需求 | 逐条确认，补充遗漏（如 headers 字段、回执字段） |
| 架构设计 | 提出三模块拆分（Ingestion API / Task Store / Dispatcher） | 审查并确认模块边界，增加 Statistics 模块 |
| 模块设计 | 草拟各模块职责、接口、表结构 | 逐模块讨论，修正不合理之处（见下方"未采纳的建议"） |
| 代码结构 | 建议项目目录结构和依赖选型 | 评估选型，确认 Go + gin + PostgreSQL 技术栈 |
| 技术细节 | 提示 `SKIP LOCKED` 任务抢占模式、指数退避公式 | 确认可行性，补充 in_flight 超时恢复机制 |

## 二、AI 给出过哪些我没有采纳的建议

### 1. Kafka + 消费者组作为任务队列

**AI 建议**：引入 Kafka 作为消息队列，用消费者组实现多 Worker 并发消费。

**不采纳理由**：MVP 流量不大，DB 轮询 + `SKIP LOCKED` 已满足并发需求。引入 Kafka 会增加部署和运维成本，且 MVP 阶段单 Worker 足够。后续流量增长时再演进。

### 2. 微服务拆分

**AI 建议**：将 Ingestion、Dispatcher、Config 拆分为独立部署的微服务。

**不采纳理由**：单服务足够处理当前规模，拆分反而增加调用链路复杂度和运维成本。微服务适合团队规模大、边界清晰的场景，MVP 阶段不需要。

### 3. 分布式事务 / 两阶段提交

**AI 建议**：使用分布式事务保证消息投递的一致性。

**不采纳理由**：通知场景不需要强一致。选择 at-least-once + 幂等设计（`notification_id` / `idempotency_key`），偶尔重复投递的代价远小于分布式事务的实现成本。

### 4. 断路器（Circuit Breaker）

**AI 建议**：引入 Hystrix/Resilience4j 断路器模式，对不可用的外部 API 熔断。

**不采纳理由**：MVP 阶段指数退避重试已足够处理临时性失败。断路器适合多供应商高频调用场景，当前规模用不上。后续供应商增多、调用量大时再引入。

### 5. 全链路可观测体系

**AI 建议**：搭建 Prometheus + Grafana + Jaeger + ELK 全链路监控。

**不采纳理由**：先用日志记录关键事件，问题暴露后再按需补齐监控。MVP 阶段不提前建设可能用不上的基础设施。

### 6. vendor_configs 表存储 Header/Body 模板

**AI 建议**：在 `vendor_configs` 表中配置 `header_template` 和 `body_template`，投递时用模板引擎渲染 payload。

**不采纳理由**：不同供应商的 Header 和 Body 差异由业务方在提交通知时直接指定，系统只做透传投递。在 vendor_configs 中配置模板会增加配置管理复杂度，且模板引擎是过度设计。最终简化为：vendor_configs 只存 HTTP 协议配置（URL、Method、超时），Header 和 Body 从请求中直接获取。

## 三、哪些关键决策是我自己做出的，以及原因

### 1. 系统边界的划定

**决策**：核心链路（接收、持久化、投递、重试）全做；权限认证、限流熔断、通知模板管理等明确划入演进路线，MVP 不做。

**原因**：面试题目考察的是工程判断能力，不是功能完整性。把有限的精力集中在投递可靠性这条主线上，比铺开做更重要。主动管理复杂度是工程成熟度的体现。

### 2. 投递语义选择 at-least-once

**决策**：选择至少一次（at-least-once），不用 exactly-once。

**原因**：分布式 exactly-once 实现代价极高，需要分布式事务或事务消息。通知场景下偶尔重复投递的代价远小于漏投递。外部供应商可用 `notification_id` 做去重。这是一个合理的工程取舍。

### 3. 4xx 直接进死信，不重试

**决策**：外部 API 返回 4xx 时，直接标记为 `dead`，不重试。

**原因**：4xx 表示请求本身有问题（鉴权失败、参数错误等），重试结果不变。只有 5xx、超时、网络错误才值得重试。区分可重试错误和不可重试错误是真实工程经验。

### 4. in_flight 超时恢复机制

**决策**：轮询查询中加入 `status = 'in_flight' AND updated_at < NOW() - INTERVAL '60 seconds'` 条件。

**原因**：Worker 可能在领取任务后、完成投递前崩溃，任务卡在 `in_flight` 状态无人处理。需要一个兜底机制让这些任务重新可被抢占。60s 阈值大于正常投递耗时但不会太长导致延迟。这个决策是 AI 未提出的，由本人根据崩溃恢复场景主动设计。

### 5. 请求中增加 headers 字段

**决策**：业务方提交通知时需要携带 `headers` 字段，投递时直接使用。

**原因**：AI 最初的方案只在 `vendor_configs` 中配置 Header 模板。但实际场景中，不同通知可能携带不同的 Header（如 Authorization token、自定义追踪 ID），这些是每次通知特有的，不适合放在供应商级别的模板中。这一修正是本人基于对实际业务场景的理解提出的。

### 6. 回执字段设计

**决策**：`notifications` 表增加 `response_status` 和 `response_body` 字段，记录每次投递的外部 API 响应。

**原因**：虽然题目说业务系统不关心返回值，但投递失败时需要排查原因。没有回执信息，死信任务无法定位是鉴权失败还是目标地址不可达。这是实际运维经验的体现。`response_body` 截断到 4KB，防止过大响应撑满存储。

### 7. 增加 Statistics 模块

**决策**：在 AI 提出的三模块架构基础上，主动增加 Statistics 统计模块。

**原因**：通知系统的核心价值是可靠投递，而验证可靠性的手段就是统计数据。成功率、失败率、重试分布是衡量系统健康度的关键指标。AI 的方案中缺少这一块，由本人补充。

### 8. 幂等去重设计

**决策**：业务方提交通知时携带 `idempotency_key`，`notifications` 表对其加唯一索引。

**原因**：业务系统因网络超时重试是常见场景。没有幂等设计会导致同一条通知被投递多次。虽然有 at-least-once 语义允许重复，但在接收端就拦截重复提交比投递后去重更高效。

### 9. 技术栈选择 Go + gin + PostgreSQL

**决策**：选择 Go 语言，gin 框架，PostgreSQL 数据库。

**原因**：Go 的并发模型适合 Worker 轮询模式，部署简单（单二进制）。PostgreSQL 的 `SKIP LOCKED` 原生支持任务抢占，JSONB 支持 headers/payload 的灵活存储。gin 轻量且社区活跃。这套组合在可靠性和开发效率之间取得了平衡。

## 四、AI 产出代码的缺陷与修复复盘

AI 生成代码的速度很快，但它不会主动替我想边界条件。本作业中 AI 产出的代码经过人工审查与测试补强后，发现并修复了 3 个足以导致线上故障的缺陷，另有第二轮审查中修复的 2 个健壮性问题。如实记录如下——这既是给 AI Coding 协同方式的最好注脚，也说明"审查"环节在人机协作中不可省略。

### 缺陷 1：死信重投触发 panic，单请求打挂整个服务

- **现象**：对不存在的 ID 调用 `POST /api/dead-letters/:id/retry`，服务直接 panic（nil 解引用）。
- **根因**：`RetryDeadLetter` 不检查 `UPDATE` 的影响行数；handler 重投后无条件调用 `GetNotification` 并读取返回值，错误返回值被丢弃，存在 nil 解引用路径。
- **发现方式**：人工代码审查——逐个追 handler 的错误处理分支时发现查询错误被忽略。
- **修复**：`RetryDeadLetter` 检查 `RowsAffected == 0` 并返回明确错误；handler 捕获查询错误返回 404 而非继续访问空对象。
- **测试**：补 `TestRetryDeadLetter_NotFound`（不存在 → 404）、`TestRetryDeadLetter_NotDeadStatus`（非 dead 状态不可重投）。

### 缺陷 2：供应商超时配置形同虚设

- **现象**：`vendor_configs.timeout_ms` 配了也不生效，所有投递共用默认超时。
- **根因**：dispatcher 构建投递请求时没有读取 `vendor.TimeoutMS`，配置在代码里没有落点。
- **发现方式**：审查投递链路——从"配置 → 请求 → 超时"逐层对照，发现超时参数没有来源。
- **修复**：按 `vendor.TimeoutMS` 用 `context.WithTimeout` 构造投递上下文（缺省 30s）。
- **测试**：补 `TestVendorTimeoutApplied`，用慢响应服务器验证超时按供应商配置生效。

### 缺陷 3：幂等去重存在并发竞态

- **现象**：相同 `idempotency_key` 并发提交时，一个请求成功，其余全部返回 500。
- **根因**：check-then-act 模式（先查是否存在、再插入），两个并发请求同时通过检查，后者的唯一约束冲突走了未处理的错误分支。
- **发现方式**：补 20 并发同 key 提交的测试稳定复现，竞态一次性暴露。
- **修复**：唯一约束冲突后重新查询并返回已有结果；MockStore 加 `sync.Mutex` 模拟唯一约束语义。
- **测试**：`TestCreateNotification_IdempotencyConcurrent`——20 并发全部返回 202 且指向同一个 `notification_id`。

### 第二轮审查：两个健壮性问题

- **请求上下文**：handler 全部使用 `context.Background()`，客户端断开后投递仍继续执行。改为 `c.Request.Context()`，请求取消即终止处理链。
- **优雅退出**：dispatcher 使用无取消的 background context + `signal.Notify`，进程收到 SIGTERM 时 Worker goroutine 被强制杀死，正在投递的任务可能丢失。改为 `signal.NotifyContext`，随信号优雅停止轮询。

### 从这些缺陷中学到什么

1. **AI 写的是"正常路径"，边界条件要靠人补**。三个缺陷全部落在边界场景（不存在的 ID、并发冲突、配置缺省），AI 默认假设一切顺利。
2. **测试是兜底工具，不是给 AI 看的**。20 并发测试一跑，check-then-act 的竞态立刻现形；没有这些测试，缺陷很可能上线后才暴露。
3. **审查要追每个错误分支**。review 时逐行问"这行如果失败会怎样"，逮到的恰恰是最贵的 bug——一个崩溃点、一个静默失效的配置、一个并发竞态。

## 五、总结

AI 在本作业中扮演了**辅助工具**的角色：帮助理解需求、草拟方案、编写代码。但所有关键工程决策——系统边界划定、投递语义选择、错误分类策略、崩溃恢复机制、表结构设计——均由本人独立判断并做出取舍。

就当前阶段 AI 的协作方式，本作业有三点体会：

- **AI 的能力**：从需求解析、架构设计到代码与文档的直接产出，AI 在每个环节都显著加快了进度，常规路径的实现质量稳定。只要 prompt 把边界和错误处理要求讲清楚，AI 也能主动覆盖这些场景——可以说，AI 承担了大部分"从想法到可运行"的工作，这是它最直接的贡献。
- **产出的遗漏**：即便如此，错误处理和边界条件仍可能被遗漏——本作业中修复的 3 个缺陷和 2 个健壮性问题，正是 prompt 未能覆盖到的边界场景。这并不说明 AI 能力不足，而是任何产出都需要人工检查这一普遍现象的体现。
- **人的作用**：把边界条件、错误处理要求显式写进 prompt，把思考传导给 AI；再对 AI 产出做人工检查，补上遗漏的场景，并对系统级取舍做最终决策。AI 负责执行，人负责把边界想清楚并验收质量。

核心理念是：**AI 提供方案，人做决策。** 工程的核心不在于方案是否"功能齐全"，而在于在有限资源下做出正确的取舍。
