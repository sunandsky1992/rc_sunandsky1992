# API 通知系统 - 取舍与演进

## 1. 不采纳的"过度设计"

| AI 容易建议的 | 为什么不采纳 |
|---|---|
| Kafka + 消费者组 | MVP 流量不大，DB 轮询 + `SKIP LOCKED` 足够，少一个中间件少一份运维 |
| 微服务拆分（Ingestion/Dispatcher/Config 各独立部署） | 单服务足够，拆了反而增加调用链路和运维成本 |
| 分布式事务/两阶段提交 | 通知场景不需要强一致，at-least-once + 幂等足够 |
| 断路器（Hystrix/Resilience4j） | MVP 阶段指数退避重试已经够用，断路器是后续多供应商场景才需要 |
| 全链路可观测体系（Prometheus+Grafana+Jaeger+ELK） | 先用日志，问题暴露了再补 |

## 2. 演进路线

```
V1（MVP）                V2（流量增长）              V3（大规模）
──────────              ──────────                  ──────────
DB 轮询            →    换 Kafka/MQ            →    分片 + 水平扩展
单进程 Worker      →    多 Worker 实例          →    Worker 池 + 自动扩缩
日志               →    Metrics + 告警         →    全链路追踪
死信手动重投       →    管理后台 + 半自动恢复   →    死信自动分析
供应商配置 DB 存   →    配置中心 + 热更新       →    多租户配置隔离
无限流             →    按供应商限流           →    熔断 + 降级
```

## 3. 触发演进的信号

- DB 轮询延迟明显 → 考虑换 MQ
- 单 Worker 处理不过来 → 多实例
- 死信堆积频繁 → 需要告警 + 自动化

## 4. 核心理念

第一版只做最小可行，让真实流量告诉我们该往哪演进。
